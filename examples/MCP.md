# omnifind MCP example

A local **stdio MCP server** using the official Rust SDK (`rmcp`), wrapping
omnifind's public API. It is an example executable, not a new library API and not
an HTTP service. There is no HTTP listener, account system, or API key storage.

Concept and project direction: **Béla István MIHALIK**.
MCP example implementation, tests, and documentation generated by **Perplexity AI**.
The repository's `AUTHORS.md` and MIT OR Apache-2.0 licensing continue to apply.

## Add to an existing checkout

Copy `mcp.rs`, `MCP.md`, and `mcp_smoke.py` into your checkout's `examples/` folder.
Add the following dependency to your **existing** `[dev-dependencies]` section;
do not create a second section with that name and do not remove the CLI's clap
dependency if you already added the earlier CLI example:

```toml
rmcp = { version = "=3.6.0", default-features = false, features = ["server", "macros", "transport-io"] }
```

Keep the existing Tokio dev-dependency with `macros` and `rt-multi-thread`.
`rmcp` enables the additional Tokio I/O and synchronization features it needs.
The crate already depends on futures, serde, serde_json, and url. JSON Schema
support is accessed through `rmcp::schemars`; no separate schemars dependency is needed.

Append this target (only once) to `Cargo.toml`:

```toml
[[example]]
name = "mcp"
path = "examples/mcp.rs"
test = true
```

Alternatively, apply the supplied patch from the repository root:

```bash
git apply --check /absolute/path/to/omnifind-mcp-example/mcp-example.patch
git apply /absolute/path/to/omnifind-mcp-example/mcp-example.patch
```

The patch was generated against `bmihalik/omnifind` commit
`b306c70af565816a41a469f7622959ac6798217e`. If your manifest has changed (for
example, because you added the CLI), use the manual integration above; do not
force the patch. No `src/` file or `AUTHORS.md` is replaced.

## Toolchain and validation

Use a current stable Rust toolchain. `rmcp 3.6.0` declares Rust 1.88 as its minimum;
the full dependency graph can require something newer. This example was tested
with Rust/Cargo 1.99.1 on Linux. **It has not been tested on Rust 1.85**, which
remains declared in the library manifest. Adding this dev-dependency increases
the toolchain requirements for testing/building examples, not the library's
public API. This delivery does not make an MSRV guarantee for the dependency graph.

```bash
rustup update stable
cargo +stable fmt --all -- --check
cargo +stable test --all-targets
cargo +stable clippy --all-targets -- -D warnings
cargo +stable build --example mcp
python3 examples/mcp_smoke.py "$PWD/target/debug/examples/mcp"
```

The Python smoke test requires only the standard library. It launches the real
MCP executable and local HTTP fixture servers; it never contacts a public search
engine. If you set `CARGO_TARGET_DIR`, substitute that target directory in the
last command. On Windows the executable has the `.exe` suffix.

Optionally build an optimized executable for everyday use:

```bash
cargo +stable build --release --example mcp
```

Run the server through an MCP host, not an interactive shell command expecting
a search prompt. It waits for MCP input on stdin and exits when stdin closes.
All stdout is reserved for MCP JSON-RPC. Put any added diagnostics on stderr.

## MCP host configuration

For a host using the common `mcpServers` configuration shape:

```json
{
  "mcpServers": {
    "omnifind": {
      "command": "/ABSOLUTE/PATH/TO/omnifind/target/release/examples/mcp",
      "env": {
        "OMNIFIND_MCP_TIMEOUT_SECONDS": "20",
        "OMNIFIND_MCP_ALLOW_EXTRACT": "0"
      }
    }
  }
}
```

Replace the command with your actual built executable's absolute path. No args
or working directory are required. Host configuration file locations and schema
vary. The example above is not a universal MCP configuration standard.

During development a host may invoke Cargo instead:

```json
{
  "mcpServers": {
    "omnifind": {
      "command": "cargo",
      "args": ["run", "--quiet", "--manifest-path", "/ABSOLUTE/PATH/TO/omnifind/Cargo.toml", "--example", "mcp"]
    }
  }
}
```

A prebuilt executable starts faster and avoids dependence on the host's Cargo PATH.
Restart your host after changing its configuration, and enable the desired tools
using that host's tool-permission settings.

## Exposed tools

| Tool | Arguments | Source / behavior |
| --- | --- | --- |
| `omnifind_search` | `query`, optional `engine`, `limit` | DuckDuckGo, Qwant, or Wikipedia; default DuckDuckGo |
| `omnifind_metasearch` | `query`, optional `engines`, `limit` | Concurrent queries; limit is per engine; exact-URL deduplication |
| `omnifind_images` | `query`, optional `limit` | DuckDuckGo Images; URLs only, no image fetching |
| `omnifind_books` | `query`, optional `limit` | Open Library books |
| `omnifind_extract` | `url`, optional `max_text_chars` | Hidden and rejected unless operator explicitly enables it |

Engine argument spellings are `duckduckgo`, `qwant`, and `wikipedia`.
Metasearch defaults to all three; repeated engines are queried once.
Nonblank queries are limited to 4096 UTF-8 bytes. `limit` defaults to 5 and must
be 1–20. Upstream caps/pagination can yield fewer than requested. Extraction
returns at most 12,000 text characters by default (configurable from 1–50,000)
and 50 links, with explicit truncation flags.

Example `tools/call` parameter objects, for inspection or use in an MCP client:

```json
{"name":"omnifind_search","arguments":{"query":"self hosted LLM","engine":"wikipedia","limit":5}}
```

```json
{"name":"omnifind_metasearch","arguments":{"query":"Rust async search","engines":["duckduckgo","qwant"],"limit":5}}
```

```json
{"name":"omnifind_books","arguments":{"query":"The Hobbit","limit":5}}
```

```json
{"name":"omnifind_images","arguments":{"query":"Budapest skyline","limit":5}}
```

```json
{"name":"omnifind_extract","arguments":{"url":"https://example.com","max_text_chars":8000}}
```

Results provide both `structuredContent` and a JSON text content block, for
clients that only display text. Search, image, and book results use an object
with `results` and `warnings`. Extraction returns `page`, `text_truncated`,
`links_truncated`, and `warnings`.

Metasearch preserves per-engine failures in `warnings`; it does not use the
library helper that silently omits failed engines. All-engine failure returns
`isError: true`, even if the result array is empty. One successful engine with
zero matches remains a success. HTTP 429, network, decoding, and other execution
failures are tool errors, not false empty successes. Raw response bodies,
credential-bearing URLs, and proxy diagnostics are not included in tool errors.

## Configuration

| Environment variable | Default | Accepted values |
| --- | --- | --- |
| `OMNIFIND_MCP_TIMEOUT_SECONDS` | `20` | Whole seconds from 1–120, per library HTTP request |
| `OMNIFIND_MCP_ALLOW_EXTRACT` | `0` | Exactly `0` or `1` |

Invalid values stop startup. Up to four tool calls run at once; extra calls
return a `busy` tool error rather than queueing indefinitely. One metasearch
call can issue up to three HTTP requests concurrently. These limits are not a
rate limiter, a global time budget, or a complete resource sandbox.

## Security and operational limits

- **URL extraction is off by default.** Set `OMNIFIND_MCP_ALLOW_EXTRACT=1` only
  for a trusted local host and trusted URLs. This enables an arbitrary-URL
  fetch capability with the network access of the server process.
- The URL check rejects non-HTTP(S) schemes and embedded credentials, but is
  **not SSRF protection**: it does not block local/private/link-local addresses,
  validate DNS resolutions, pin destination IPs, or revalidate redirects.
  Use a sandbox and egress firewall if enabling extraction. Do not expose this
  example as an untrusted multi-user or public service without hardening it.
- Query text goes to third-party search services. Do not submit secrets. Engine
  services may rate-limit, block automation, change formats, or require compliance
  with their usage policies. There is no automatic retry/fallback policy here.
- Snippets and extracted pages are untrusted external content. They can contain
  prompt injection; treat them as data rather than executable instructions.
  Read-only tool annotations are advisory, not a permission system.
- Serialized structured success data is limited to 256 KiB; oversize responses
  become tool errors. Text duplication for compatibility means the total JSON-RPC
  response can exceed 256 KiB. This is an output limit, **not a download/memory cap**.
  The library still fetches and parses the full upstream page/response in memory.
  No maximum incoming JSON-RPC line size is added by this example.
- Extraction is HTML parsing, not JavaScript rendering or a browser/readability
  service. There is no robots.txt handling or crawl scheduler in this example.
- This is stdio only. No Streamable HTTP transport or authentication is supplied.

## Tested protocol behavior

The included smoke test verifies traditional initialization for protocol revisions
`2025-06-18` and `2025-11-25`, plus `2026-07-28` discovery and per-request metadata.
It also exercises tool discovery, argument schemas, tool-error reporting, opt-in
extraction, Unicode truncation, HTTP 404 handling, and clean EOF shutdown.
Public-engine success is not asserted by this test.
